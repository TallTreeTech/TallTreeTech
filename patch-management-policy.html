1. Purpose and Scope

1.1 Purpose

This policy establishes requirements and procedures for managing security updates and patches across all IT systems. Timely patching is essential to protect against known vulnerabilities and is a core requirement of the UK Cyber Essentials scheme. This policy ensures that security updates are identified, assessed, tested, and deployed systematically.

1.2 Scope

This policy applies to security updates and patches for:

  • Operating systems (Windows, macOS, Linux, mobile operating systems)
  • Applications and software (browsers, office applications, PDF readers, etc.)
  • Server software (web servers, database servers, mail servers)
  • Network devices (firewalls, routers, switches, wireless access points)
  • Firmware (BIOS/UEFI, device firmware)
  • Security software (anti-malware, endpoint protection)
  • Cloud services where the Company manages updates
  • Development frameworks and libraries used in Company applications

1.3 Policy Statement

The Company shall maintain a systematic patch management program to ensure that security updates are applied promptly to all systems. Patches addressing critical and high-severity vulnerabilities shall be prioritized and deployed according to defined timescales. All systems within scope must be kept up to date with security patches.

2. Patch Management Framework

2.1 Patch Management Lifecycle

1. Identification

Monitor vendor security bulletins, advisories, and automated tools to identify available patches.

2. Assessment

Evaluate patch severity, applicability, and potential impact on systems.

3. Acquisition

Obtain patches from official vendor sources or trusted repositories.

4. Testing

Test patches in non-production environment to identify potential issues.

5. Approval

Approve patches for deployment based on testing results and risk assessment.

6. Deployment

Deploy patches to production systems according to priority and schedule.

7. Verification

Verify successful installation and system functionality after patching.

8. Documentation

Document patch deployment, issues encountered, and current patch status.

2.2 Patch Management Principles

Risk-Based Prioritization

Patches shall be prioritized based on vulnerability severity, exploitability, and asset criticality. Critical vulnerabilities affecting internet-facing systems receive highest priority.

Timely Deployment

Security patches must be deployed within defined timescales based on severity. Delays increase risk of exploitation.

Testing Before Production

Patches should be tested before production deployment where practical. Balance testing thoroughness with urgency of patching.

Comprehensive Coverage

All systems, applications, and devices must be included in patch management. No systems should be overlooked.

Automated Where Possible

Automation should be used to improve timeliness and consistency of patching while maintaining appropriate controls.

3. Patch Deployment Timescales

3.1 Cyber Essentials Requirements

To maintain Cyber Essentials compliance, security updates must be applied according to the following timescales:

Severity Level Description Maximum Deployment Time Examples
Critical Severe vulnerabilities with active exploitation or high likelihood of exploitation. Could allow complete system compromise. 14 days from release Remote code execution, privilege escalation, actively exploited zero-days
High Significant security vulnerabilities that could lead to system compromise but may require specific conditions. 30 days from release Authentication bypass, information disclosure of sensitive data, DoS vulnerabilities
Medium Moderate security issues with limited impact or requiring significant attacker access. 90 days from release Cross-site scripting, limited information disclosure, local privilege escalation
Low Minor security issues or feature updates with security improvements. As practical (within 180 days recommended) Hardening improvements, security feature additions, minor fixes

3.2 Accelerated Patching

The following situations require accelerated patching (target 48-72 hours):

  • Vulnerabilities with active exploitation in the wild
  • Zero-day vulnerabilities affecting the Company's systems
  • Vulnerabilities affecting internet-facing systems
  • Vulnerabilities for which exploit code is publicly available
  • Worm-able vulnerabilities (e.g., WannaCry, NotPetya scenarios)

3.3 Automatic Updates

Automatic updates shall be enabled for:

  • Workstations: Windows Update, macOS Software Update (for security updates)
  • Browsers: Automatic updates enabled for Chrome, Edge, Firefox
  • Anti-malware: Automatic definition and engine updates
  • Mobile devices: Automatic security updates enabled where available
  • SaaS applications: Vendor-managed updates (no action required from Company)

3.4 Controlled Updates

The following require controlled deployment (not automatic):

  • Server operating system updates
  • Database patches
  • Network device firmware
  • Application server patches
  • Business-critical application updates

4. Patch Management Process

4.1 Patch Identification and Monitoring

4.1.1 Information Sources

The IT team shall monitor the following sources for security updates:

  • Microsoft: Windows Update, WSUS, Microsoft Security Response Center
  • Apple: macOS and iOS security updates page
  • Linux: Distribution security mailing lists and update repositories
  • Application vendors: Security bulletins and update notifications
  • Security advisories: NCSC alerts, US-CERT, vendor-specific advisories
  • Vulnerability databases: CVE, NVD (National Vulnerability Database)
  • Automated tools: Patch management systems, vulnerability scanners

4.1.2 Automated Scanning

  • Vulnerability scanning tools deployed to identify missing patches
  • Scans performed weekly (minimum) on all managed systems
  • Results reviewed and prioritized by IT team
  • Critical findings trigger immediate action

4.2 Patch Assessment

4.2.1 Severity Rating

Patches shall be rated based on:

  • Vendor severity rating: Critical, Important/High, Moderate/Medium, Low
  • CVSS score: Common Vulnerability Scoring System score (0-10)
  • Exploitability: Is exploit code available? Is it being exploited?
  • Attack vector: Network accessible, adjacent network, local, or physical

4.2.2 Applicability Assessment

For each patch, determine:

  • Which Company systems are affected
  • Number of systems requiring the patch
  • Criticality of affected systems
  • Current exposure (internet-facing, internal, isolated)

4.2.3 Impact Assessment

Evaluate potential impact of patch deployment:

  • Required system restart or service interruption
  • Known compatibility issues
  • Application dependencies
  • Potential performance impact
  • Testing requirements

4.3 Patch Testing

4.3.1 Test Environment

The Company shall maintain test environments that mirror production for:

  • Critical servers and applications
  • Standard desktop/laptop configurations
  • Network infrastructure (where practical)

4.3.2 Testing Procedures

Patch Severity Testing Requirements Testing Duration
Critical (exploited in wild) Minimal testing - basic functionality only 1-2 hours
Critical (not yet exploited) Basic functionality and application compatibility 1-2 days
High Functionality, compatibility, and limited performance testing 3-5 days
Medium/Low Comprehensive testing including edge cases 1-2 weeks

4.3.3 Testing Activities

  • Installation testing: Verify patch installs without errors
  • Functionality testing: Confirm system and applications work as expected
  • Compatibility testing: Test integration with other systems and applications
  • Performance testing: Verify no significant performance degradation
  • Rollback testing: Confirm ability to uninstall/rollback if needed

4.3.4 Testing Exceptions

Limited or no testing may be performed when:

  • Patch addresses actively exploited vulnerability
  • Test environment not available (automatic client updates)
  • Vendor recommends immediate deployment
  • Compensating controls insufficient to mitigate risk

In these cases, closely monitor production deployment and be prepared for rapid rollback.

4.4 Patch Approval

4.4.1 Approval Authority

Patch Scope Approval Required
Automatic client updates (workstations, browsers) Pre-approved (policy sets framework)
Server patches (routine, tested) IT Director or delegate
Emergency patches IT Director (with retrospective executive notification)
Patches affecting critical business systems IT Director + Business System Owner
Patches requiring significant downtime IT Director + Executive Management

4.4.2 Approval Criteria

Patches approved for deployment when:

  • Testing completed successfully (or testing exception applies)
  • No critical issues identified
  • Deployment plan prepared
  • Rollback procedures documented
  • Business impact assessed and acceptable
  • Change management requirements met

4.5 Patch Deployment

4.5.1 Deployment Methods

System Type Deployment Method
Windows Workstations WSUS, Microsoft Endpoint Manager, or Windows Update
macOS Workstations Apple Software Update, MDM, or Jamf
Linux Systems Package manager (apt, yum, dnf), Ansible, or manual
Windows Servers WSUS, manual deployment during maintenance windows
Network Devices Manual deployment following vendor procedures
Cloud Services Vendor-managed or infrastructure-as-code tools

4.5.2 Deployment Staging

Patches shall be deployed in stages to minimize risk:

  1. Pilot group: Small number of representative systems (5-10% of population)
  2. Monitor: Verify successful deployment and no issues (24-48 hours)
  3. Phased rollout: Deploy to larger groups progressively
  4. Complete deployment: Deploy to remaining systems

Exception: Critical patches for actively exploited vulnerabilities may skip staging for rapid deployment.

4.5.3 Deployment Timing

  • Workstations: During off-hours or allow user-initiated restarts
  • Non-critical servers: During standard maintenance windows (e.g., weekends)
  • Critical servers: During planned maintenance windows with business approval
  • Network devices: During scheduled maintenance windows with redundancy in place

4.5.4 Deployment Communication

Users and stakeholders shall be notified:

  • 48-72 hours advance notice for planned maintenance
  • Notification of required system restarts
  • Expected downtime and service availability
  • Contact information for issues
  • Emergency patches may have shorter notice periods

4.6 Verification and Reporting

4.6.1 Post-Deployment Verification

After patch deployment, verify:

  • Patch installed successfully on target systems
  • Systems rebooted if required
  • Applications and services functioning normally
  • No unexpected issues or errors
  • Users able to work without problems

4.6.2 Failed Deployments

When patch deployment fails:

  • Document the failure and error messages
  • Investigate root cause
  • Implement remediation (fix issue, alternative patch, compensating controls)
  • Retry deployment after resolution
  • Escalate if unable to resolve

4.6.3 Rollback Procedures

If patch causes issues in production:

  • Assess severity of issue vs. security risk of unpatching
  • Uninstall patch using tested rollback procedure if needed
  • Implement compensating controls (firewall rules, access restrictions)
  • Investigate issue and test alternative approaches
  • Report issue to vendor if appropriate

5. Emergency Patching

5.1 Emergency Patch Criteria

Emergency patching procedures activated when:

  • Critical vulnerability actively being exploited
  • Worm-able vulnerability affecting Company systems
  • Zero-day vulnerability with available patch
  • Vendor issues emergency security update with urgent recommendation
  • Company systems compromised due to unpatched vulnerability

5.2 Emergency Patching Process

  1. Notification: IT Director notified immediately of emergency situation
  2. Assessment: Rapid assessment of impact and affected systems (1-2 hours)
  3. Decision: IT Director decides on emergency patching approach
  4. Preparation: Obtain patches, prepare deployment, document rollback
  5. Testing: Minimal testing (1-2 hours) - basic functionality only
  6. Approval: IT Director approval (verbal acceptable, document later)
  7. Deployment: Deploy to all affected systems as quickly as possible
  8. Monitoring: Intensive monitoring during and after deployment
  9. Communication: Update executive management and affected users
  10. Documentation: Document actions taken and lessons learned

5.3 Emergency Response Time

Target emergency patch deployment timescales:

  • Internet-facing systems: 24-48 hours from patch availability
  • Internal systems: 48-72 hours from patch availability
  • Isolated systems: 72 hours or implement isolation/compensating controls

6. Patch Inventory Management

6.1 Asset Inventory

The Company shall maintain an inventory of all assets requiring patching:

  • Hardware devices and their operating systems
  • Installed applications and versions
  • Network devices and firmware versions
  • Cloud services and subscription levels
  • Asset owners and criticality ratings

6.2 Patch Status Tracking

For each system, track:

  • Current patch level/version
  • Missing patches (categorized by severity)
  • Last patch date
  • Scheduled patch maintenance
  • Exceptions and compensating controls

6.3 Software Lifecycle Management

6.3.1 Unsupported Software

Software that no longer receives security updates must not be used (Cyber Essentials requirement):

  • Operating systems beyond end-of-support (e.g., Windows 7, Windows Server 2008)
  • Applications no longer supported by vendor
  • Outdated software versions multiple generations behind current

6.3.2 End-of-Life Planning

For software approaching end-of-support:

  • Identify affected systems 12 months before EOL
  • Create migration plan with timeline and budget
  • Test replacement software/systems
  • Migrate before support ends
  • If migration delayed, isolate unsupported systems from network

7. Patch Management Metrics and Reporting

7.1 Key Performance Indicators

Metric Target Reporting Frequency
Critical patches deployed within 14 days 100% Monthly
High severity patches deployed within 30 days ≥95% Monthly
All systems current on patches ≥90% Monthly
Time to deploy emergency patches ≤48 hours Per incident
Systems with no unsupported software 100% Quarterly
Patching-related system outages ≤2 per year Quarterly

7.2 Compliance Reporting

Patch compliance reports shall include:

  • Executive summary: Overall compliance status and key metrics
  • Compliance by severity: Percentage of systems patched for critical/high/medium
  • Overdue patches: Systems with patches past deployment deadline
  • Exceptions: Approved exceptions and compensating controls
  • Trends: Compliance trends over time
  • Issues: Barriers to patching and remediation plans

7.3 Reporting Schedule

  • IT Management: Weekly patch status dashboard
  • IT Director: Monthly compliance report
  • Executive Management: Quarterly summary report
  • Board of Directors: Annual patch management review
  • Cyber Essentials Assessment: Patch compliance evidence as required

8. Compensating Controls

8.1 When Patches Cannot Be Deployed

If a security patch cannot be deployed within required timescales due to technical or business constraints, compensating controls must be implemented:

8.1.1 Network Isolation

  • Isolate vulnerable system from internet and untrusted networks
  • Place on separate VLAN with restricted access
  • Allow only necessary communication through firewall rules

8.1.2 Additional Monitoring

  • Enhanced logging and monitoring of vulnerable system
  • Intrusion detection/prevention rules specific to vulnerability
  • More frequent review of security logs

8.1.3 Access Restrictions

  • Limit user access to system (only essential personnel)
  • Disable unnecessary services and features
  • Enhanced authentication requirements

8.1.4 Virtual Patching

  • Deploy IPS signatures to block exploitation attempts
  • Use web application firewall rules to filter malicious requests
  • Implement endpoint protection rules

8.2 Documentation Requirements

Compensating controls must be documented with:

  • System identification and vulnerability details
  • Reason patch cannot be deployed
  • Risk assessment
  • Specific compensating controls implemented
  • Timeline for patch deployment
  • Approval from IT Director
  • Regular review schedule (at least monthly)

9. Roles and Responsibilities

9.1 IT Director

  • Overall accountability for patch management program
  • Approve patch management procedures and schedules
  • Approve exceptions and compensating controls
  • Allocate resources for patching activities
  • Review patch compliance reports
  • Escalate compliance issues to executive management
  • Authorize emergency patching activities

9.2 System Administrators

  • Monitor for available security patches
  • Assess and prioritize patches
  • Test patches in appropriate environments
  • Deploy patches according to schedules and procedures
  • Verify successful patch installation
  • Document patching activities
  • Report compliance status
  • Maintain patch management tools

9.3 Application Owners

  • Identify patches affecting their applications
  • Participate in patch testing for their applications
  • Approve patches that may impact business operations
  • Coordinate maintenance windows for critical systems
  • Report application issues after patching

9.4 All Users

  • Allow automatic updates on workstations
  • Restart systems when prompted for updates
  • Report issues after patching promptly
  • Comply with maintenance window schedules
  • Keep personal devices used for work up to date

10. Training and Awareness

10.1 Technical Training

IT staff responsible for patching shall receive training on:

  • Patch management tools and systems
  • Vulnerability assessment and prioritization
  • Testing procedures and rollback
  • Emergency response procedures
  • Vendor-specific patching processes

10.2 User Awareness

All users shall be educated on:

  • Importance of security updates
  • Not delaying or ignoring update prompts
  • Restarting devices when updates require it
  • Reporting update-related issues

11. Policy Review and Maintenance

11.1 Review Schedule

This policy shall be reviewed:

  • Annually as a minimum
  • When Cyber Essentials requirements change
  • After significant patching failures or security incidents
  • When new system types are introduced
  • When patching tools or processes change significantly

11.2 Continuous Improvement

The patch management program shall be continuously improved through:

  • Post-incident reviews of patching-related issues
  • Regular process audits
  • Stakeholder feedback
  • Adoption of improved tools and automation
  • Industry best practice benchmarking

Important Cyber Essentials Requirement

Unsupported software and operating systems must not be used. Systems that no longer receive security updates from vendors cannot be certified under Cyber Essentials and present significant security risk.

Current examples of unsupported software that must not be used:

  • Windows 7, Windows 8, Windows Server 2008/2012 (unless Extended Security Updates active)
  • macOS versions more than 2 years old
  • Internet Explorer
  • Any application no longer supported by vendor
