1. Purpose and Scope

1.1 Purpose

This policy establishes requirements for managing user access to the Company's information systems, applications, and data. It ensures that access is granted based on business need, follows the principle of least privilege, and is appropriately controlled to protect against unauthorized access.

1.2 Scope

This policy applies to:

  • All employees, contractors, consultants, and third parties requiring access to the Company's systems
  • All IT systems, applications, databases, and network resources
  • All access methods including on-site, remote, and cloud-based access
  • All types of accounts including user accounts, administrative accounts, service accounts, and application accounts

1.3 Policy Statement

The Company shall implement appropriate access controls to ensure that only authorized individuals can access systems and data, and only to the extent necessary for their legitimate business purposes. Access controls must support confidentiality, integrity, and availability of information assets.

2. Access Control Principles

2.1 Least Privilege

Users shall be granted the minimum level of access required to perform their job functions. Access beyond this minimum must be specifically justified and approved.

2.2 Need to Know

Access to information shall be granted only when there is a legitimate business need to access that information.

2.3 Separation of Duties

Where practical, duties shall be segregated to prevent conflicts of interest and reduce the risk of fraud or error. No single individual should have control over all phases of a critical transaction or process.

2.4 Defense in Depth

Multiple layers of access controls shall be implemented, including network controls, application controls, and data controls.

3. User Account Management

3.1 Account Creation Process

3.1.1 Standard User Accounts

New user accounts shall be created according to the following process:

  1. Request: Line manager submits access request using the approved access request form
  2. Justification: Request must include:
    • User's name and job title
    • Start date and duration (if temporary)
    • Systems and applications required
    • Access level required with business justification
    • Reference user (someone with similar access requirements)
  3. Approval:
    • Line manager approval (confirms business need)
    • IT Director approval (confirms appropriate access level)
    • Data owner approval (for access to sensitive systems or data)
  4. Implementation: IT team creates account with approved access rights
  5. Documentation: Access request and approvals retained for audit purposes
  6. Communication: User provided with account details and security requirements

3.1.2 Administrative Accounts

Administrative accounts require enhanced controls:

  • Limited number: Granted only when regular user access is insufficient
  • Named accounts: Each administrator must have a separate admin account (no shared admin accounts)
  • Naming convention: Clearly identified as administrative (e.g., "admin-" prefix)
  • Additional approval: Requires approval from IT Director and a member of senior management
  • Annual review: Administrative access reviewed annually to confirm continued need
  • Enhanced monitoring: Activities performed with administrative accounts are logged and monitored

Important: Separate Accounts Required

Users requiring administrative access must have two separate accounts:

  • Standard user account: For day-to-day work (email, documents, normal applications)
  • Administrative account: Only used when administrative privileges are needed

Administrative accounts must NOT be used for regular activities such as email or web browsing.

3.2 Account Types

3.2.1 Standard User Accounts

  • For day-to-day business activities
  • Limited privileges appropriate to job role
  • Subject to standard password and MFA requirements

3.2.2 Administrative/Privileged Accounts

  • For system administration and configuration
  • Enhanced security requirements including mandatory MFA
  • Activities logged and monitored
  • Separate from standard user accounts

3.2.3 Service Accounts

  • Used by applications and automated processes
  • Not for interactive login by users
  • Strong passwords (minimum 20 characters) managed securely
  • Documented with owner and purpose
  • Reviewed quarterly

3.2.4 Emergency Access Accounts

  • Break-glass accounts for emergency access to critical systems
  • Credentials stored securely in sealed envelope or secure password vault
  • Any use triggers immediate investigation and password change
  • Tested quarterly to ensure functionality

3.2.5 Temporary/Contractor Accounts

  • Created with defined expiration date
  • Access limited to specific systems as needed
  • Subject to same security requirements as employee accounts
  • Automatically disabled on expiration date

3.3 Prohibited Account Types

The following account types are prohibited:

  • Shared accounts: Each user must have a unique account (exceptions require IT Director approval with compensating controls)
  • Generic accounts: Accounts such as "admin", "user", "test" must not be used
  • Guest accounts: Must be disabled on all systems
  • Anonymous access: Must be disabled except where specifically required and approved

4. Password Requirements

4.1 Password Strength

All user passwords must meet the following minimum requirements:

Account Type Minimum Length Complexity MFA Required
Standard User Accounts 12 characters Mix of upper, lower, numbers, symbols Yes (remote access)
Administrative Accounts 14 characters Mix of upper, lower, numbers, symbols Yes (all access)
Service Accounts 20 characters Randomly generated N/A
Emergency Access 16 characters Randomly generated Yes

4.2 Password Composition

Passwords must:

  • Contain at least one uppercase letter (A-Z)
  • Contain at least one lowercase letter (a-z)
  • Contain at least one number (0-9)
  • Contain at least one special character (!@#$%^&* etc.)
  • Not contain the user's name or username
  • Not contain common dictionary words
  • Not be a commonly used password (checked against breach databases)

4.3 Password Management

  • Password changes:
    • Must be changed immediately when compromised or suspected compromise
    • Should be changed if account shows suspicious activity
    • No routine mandatory changes required (unless password is weak or compromised)
  • Password reuse: Previous 10 passwords cannot be reused
  • Default passwords: Must be changed before account can be used
  • Password storage:
    • Users may use approved password managers
    • Passwords must never be written down or shared
    • Passwords must never be sent via email or instant message
    • Passwords must not be stored in browsers without additional protection
  • Password reset:
    • Self-service password reset available using approved methods
    • Identity verification required for IT support password resets
    • Temporary passwords must be changed on first login

4.4 Account Lockout

To prevent brute force attacks:

  • Accounts must be locked after a maximum of 10 failed login attempts
  • Lockout duration: 30 minutes or until administrator unlocks
  • Lockout events must be logged and reviewed
  • Repeated lockouts investigated as potential security incidents

5. Multi-Factor Authentication (MFA)

5.1 MFA Requirements

Multi-factor authentication must be enabled for:

  • All administrative and privileged accounts (no exceptions)
  • Remote access to Company systems (VPN, RDP, SSH, etc.)
  • Access to cloud services and SaaS applications
  • Email systems (webmail and mobile access)
  • Access to financial systems
  • Access to systems containing sensitive personal data

5.2 MFA Methods

Approved MFA methods include:

  • Preferred: Authenticator apps (Microsoft Authenticator, Google Authenticator, Duo)
  • Acceptable: Hardware tokens (YubiKey, etc.)
  • Acceptable: Push notifications to registered mobile device
  • Discouraged: SMS codes (use only if no other option available)

5.3 MFA Registration and Recovery

  • Users must register MFA methods during account setup or first login
  • Multiple MFA methods should be registered where possible
  • Backup codes must be generated and stored securely
  • MFA reset requires identity verification by IT support

6. Access Reviews

6.1 Regular Access Reviews

User access rights must be reviewed according to the following schedule:

Review Type Frequency Reviewer
All User Accounts Quarterly Line Managers
Administrative Accounts Quarterly IT Director
Service Accounts Quarterly System Administrators
Sensitive Data Access Monthly Data Owners
External/Third Party Access Monthly IT Director

6.2 Review Process

During access reviews, reviewers must:

  1. Verify that each user still requires access
  2. Confirm that access levels are appropriate for current job role
  3. Identify any unnecessary or excessive access
  4. Request removal of access that is no longer needed
  5. Document the review with findings and actions taken

6.3 Inactive Account Review

  • Accounts with no login activity for 60 days must be reviewed
  • Accounts inactive for 90 days must be disabled (unless documented exception)
  • Disabled accounts may be deleted after 180 days

7. Account Deactivation and Removal

7.1 Employee Termination

When employment ends:

  • Immediate action (within 1 hour of notification):
    • Disable all user accounts
    • Revoke VPN and remote access
    • Disable access cards and physical access
  • Within 24 hours:
    • Remove from all security groups and distribution lists
    • Revoke access to cloud services
    • Disable mobile device access
    • Change passwords on any shared accounts the user knew
  • Within 1 week:
    • Transfer ownership of files and data as appropriate
    • Archive mailbox if required
    • Complete documentation of access removal
  • After 30 days:
    • Delete account (unless legal or business requirement to retain)

7.2 Role Changes

When an employee changes role:

  • Line manager notifies IT of role change
  • New access requirements identified
  • Old access that is no longer needed is removed
  • New access is granted following normal approval process
  • Changes documented in access management system

7.3 Contractor/Third Party Access

For external parties:

  • Access granted for specified time period only
  • Expiration date set on account creation
  • System automatically disables account on expiration
  • Sponsoring employee responsible for requesting extension if needed
  • Access revoked immediately if contract/agreement ends early

8. Remote Access Controls

8.1 Remote Access Requirements

All remote access to the Company's systems must:

  • Use approved VPN or secure gateway solutions
  • Require multi-factor authentication
  • Use encrypted connections (TLS 1.2 or higher)
  • Be from devices that meet security requirements (encryption, anti-malware, patches)
  • Be logged and monitored

8.2 Remote Access Methods

Access Method Use Case Requirements
VPN (Virtual Private Network) General remote access to internal network Approved VPN client, MFA, managed device
Web-based Applications Access to cloud services and SaaS HTTPS only, MFA, supported browser
Remote Desktop (RDP) Remote administration VPN required, MFA, admin account, logged
SSH Server administration Key-based auth, MFA, VPN required, logged

8.3 Third Party Remote Access

When third parties require remote access for support or development:

  • Access must be time-limited (specific dates/times)
  • Access requires approval from IT Director
  • Third party must comply with Company security requirements
  • Access sessions must be monitored or supervised
  • All activities logged
  • Access revoked immediately after work completion

9. Special Access Controls

9.1 Sensitive Data Access

Access to sensitive data categories requires additional controls:

  • Personal data: Data protection impact assessment, role-based access, audit logging
  • Financial data: Segregation of duties, approval workflows, reconciliation controls
  • Commercial confidential: NDA required, need-to-know principle, DLP controls
  • Security information: Strictly limited access, clearance required

9.2 Database Access

  • Direct database access limited to database administrators
  • Application access via service accounts only
  • Production database access requires specific justification and approval
  • All database queries logged (especially on production)
  • Development/test databases must not contain real personal data

9.3 Source Code Access

  • Read access: Developers and relevant technical staff
  • Write access: Subject to code review and version control
  • Production deployment access: Limited to authorized deployment team
  • All code changes tracked and attributed to named users

10. Roles and Responsibilities

10.1 IT Director

  • Overall responsibility for access control policy and implementation
  • Approve administrative access requests
  • Review access control logs and reports
  • Investigate access control violations
  • Report on access control compliance

10.2 Line Managers

  • Request access for team members
  • Ensure access requests are appropriate and justified
  • Participate in quarterly access reviews
  • Notify IT immediately when team members leave or change roles

10.3 IT Support Team

  • Implement approved access requests
  • Maintain access management documentation
  • Monitor for suspicious account activity
  • Perform regular account maintenance (disable inactive accounts, etc.)

10.4 All Users

  • Protect passwords and authentication credentials
  • Use only assigned accounts (no sharing)
  • Report lost or stolen credentials immediately
  • Report suspicious account activity
  • Comply with all access control requirements
  • Only access systems and data required for job duties

11. Monitoring and Compliance

11.1 Access Logging

The following access events must be logged:

  • Successful and failed login attempts
  • Use of administrative privileges
  • Access to sensitive data
  • Account creation, modification, and deletion
  • Permission changes
  • Remote access connections

11.2 Log Review

  • Security logs reviewed weekly for anomalies
  • Failed login attempts investigated
  • Unusual access patterns flagged for review
  • Administrative account usage reviewed monthly

11.3 Policy Violations

Violations of this policy may result in:

  • Account suspension or termination
  • Disciplinary action up to and including termination of employment
  • Legal action for unauthorized access
  • Reporting to law enforcement if criminal activity suspected

12. Policy Review

This policy shall be reviewed:

  • Annually as a minimum
  • Following security incidents involving access control
  • When significant changes are made to IT systems
  • When regulatory requirements change
