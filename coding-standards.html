Purpose

This document establishes comprehensive coding standards and software development best practices for all TallTree Technologies projects. These standards ensure code quality, maintainability, security, and consistency across our development teams and client deliverables.

Scope: All software development, including internal tools, client projects, open source contributions, and prototypes.

Compliance: All developers, contractors, and third-party contributors working on TallTree Technologies projects must adhere to these standards. Exceptions require written approval from the Technical Lead or Director.

1. Code Quality Principles

1.1 SOLID Principles

All object-oriented code must follow SOLID design principles:

Principle Description Application
Single Responsibility A class should have one reason to change Each class/module has one well-defined purpose
Open/Closed Open for extension, closed for modification Use interfaces, abstract classes, and composition
Liskov Substitution Subtypes must be substitutable for base types Inheritance must not violate base class contracts
Interface Segregation No client should depend on unused methods Create specific, focused interfaces
Dependency Inversion Depend on abstractions, not concretions Use dependency injection and interfaces

1.2 DRY (Don't Repeat Yourself)

Principle: Every piece of knowledge must have a single, unambiguous representation in the system.

Application:

  • Extract repeated code into reusable functions/methods
  • Use configuration files for repeated constants
  • Create shared libraries for common functionality
  • Avoid copy-paste programming
Exception: Sometimes duplication is preferable to the wrong abstraction. If code is similar but serves different purposes or is likely to diverge, duplication may be appropriate.

1.3 KISS (Keep It Simple, Stupid)

Principle: Simplicity should be a key goal in design; unnecessary complexity should be avoided.

Guidelines:

  • Choose simple solutions over clever ones
  • Write code for humans first, computers second
  • Avoid premature optimization
  • Question complex abstractions
  • Break complex problems into simple steps

1.4 YAGNI (You Aren't Gonna Need It)

Principle: Don't add functionality until it is necessary.

Application:

  • Implement features when required, not in anticipation
  • Avoid speculative generality
  • Focus on current requirements
  • Refactor when new requirements emerge

1.5 Separation of Concerns

Organize code into distinct sections, each addressing a separate concern:

  • Presentation Layer: UI/UX components
  • Business Logic Layer: Core application logic
  • Data Access Layer: Database and external service interactions
  • Infrastructure: Configuration, logging, monitoring

// TypeScript example with proper typing
interface User {
  id: number;
  email: string;
  firstName: string;
  lastName: string;
  createdAt: Date;
}

interface UserService {
  getUser(id: number): Promise<User>;
  createUser(data: Omit<User, 'id' | 'createdAt'>): Promise<User>;
}

class UserServiceImpl implements UserService {
  async getUser(id: number): Promise<User> {
    // Implementation
    const response = await fetch(`/api/users/${id}`);
    return response.json();
  }

  async createUser(data: Omit<User, 'id' | 'createdAt'>): Promise<User> {
    // Implementation
    const response = await fetch('/api/users', {
      method: 'POST',
      body: JSON.stringify(data),
      headers: { 'Content-Type': 'application/json' }
    });
    return response.json();
  }
}

2.5 SQL Standards

Style Guide

  • SQL keywords in UPPERCASE
  • Table and column names in snake_case
  • Indent subqueries and nested logic
  • Use explicit JOIN syntax (not comma-separated tables)
-- Good SQL formatting
SELECT
    u.user_id,
    u.email,
    u.first_name,
    u.last_name,
    COUNT(o.order_id) AS total_orders
FROM users u
LEFT JOIN orders o ON u.user_id = o.user_id
WHERE u.created_at >= '2025-01-01'
    AND u.status = 'active'
GROUP BY
    u.user_id,
    u.email,
    u.first_name,
    u.last_name
HAVING COUNT(o.order_id) > 5
ORDER BY total_orders DESC;

3. Documentation Requirements

3.1 Inline Code Comments

When to Comment

  • Complex algorithms: Explain the approach and reasoning
  • Non-obvious code: Clarify intent when code is not self-explanatory
  • Workarounds: Document temporary solutions and technical debt
  • Business logic: Explain business rules and domain concepts
  • Performance considerations: Document optimization decisions

When NOT to Comment

  • Self-explanatory code (good naming makes comments unnecessary)
  • Obvious operations
  • Commented-out code (delete it; Git preserves history)

Comment Standards

// Bad: Obvious comment
// Increment counter
counter++;

// Good: Explains why, not what
// Reset counter every 1000 requests to prevent overflow
// See: https://jira.example.com/PROJ-1234
if (counter >= 1000) {
    counter = 0;
}

6. Testing Requirements

6.1 Unit Testing

Requirements:

  • Minimum Coverage: 80% code coverage for new code
  • Test Naming: Descriptive names explaining what is tested
  • Test Structure: Arrange-Act-Assert pattern
  • Independence: Tests must not depend on execution order
  • Speed: Unit tests should run quickly (under 1 second each)

Example (Python with pytest)

def test_calculate_discount_applies_gold_member_bonus():
    """Gold members should receive additional 5% discount."""
    # Arrange
    price = 100.0
    discount_rate = 0.1
    member_tier = 'gold'

    # Act
    final_price = calculate_discount(price, discount_rate, member_tier)

    # Assert
    assert final_price == 85.0  # 10% + 5% bonus


def test_calculate_discount_raises_error_for_negative_price():
    """Should raise ValueError for negative prices."""
    # Arrange, Act, Assert
    with pytest.raises(ValueError, match="price must be positive"):
        calculate_discount(-10.0, 0.1, 'silver')

7. Security Coding Practices

7.1 OWASP Top 10 Compliance

All code must be developed with OWASP Top 10 security risks in mind:

Risk Mitigation
Injection (SQL, NoSQL, OS) Use parameterized queries, ORMs, input validation
Broken Authentication Use strong password policies, MFA, secure session management
Sensitive Data Exposure Encrypt data at rest and in transit, use HTTPS
XML External Entities (XXE) Disable XML external entity processing
Broken Access Control Implement proper authorization checks on all endpoints
Security Misconfiguration Harden configurations, disable unnecessary features
Cross-Site Scripting (XSS) Sanitize input, escape output, use Content Security Policy
Insecure Deserialization Validate serialized data, use safe serialization formats
Using Components with Known Vulnerabilities Keep dependencies updated, use vulnerability scanning
Insufficient Logging & Monitoring Log security events, monitor for suspicious activity

7.2 Input Validation

Principles:

  • Validate all input: Never trust user input or external data
  • Whitelist validation: Allow known good, reject everything else
  • Server-side validation: Never rely solely on client-side validation
  • Sanitize input: Remove or encode dangerous characters
// Example: Input validation in TypeScript
function validateEmail(email: string): boolean {
  const emailRegex = /^[^\s@]+@[^\s@]+\.[^\s@]+$/;

  if (!email || typeof email !== 'string') {
    throw new ValidationError('Email is required');
  }

  if (email.length > 255) {
    throw new ValidationError('Email too long');
  }

  if (!emailRegex.test(email)) {
    throw new ValidationError('Invalid email format');
  }

  return true;
}

7.3 Authentication and Authorization

  • Use established libraries: Don't roll your own crypto
  • Hash passwords: Use bcrypt, scrypt, or Argon2
  • Secure session tokens: Use cryptographically random tokens
  • Implement rate limiting: Prevent brute force attacks
  • Use HTTPS only: Never transmit credentials over HTTP
  • Implement MFA: For sensitive operations

7.4 Secrets Management

NEVER commit secrets to version control!

Best Practices:

  • Use environment variables for secrets
  • Use secret management services (AWS Secrets Manager, Azure Key Vault)
  • Rotate secrets regularly
  • Use different secrets for different environments
  • Provide .env.example with dummy values
# .env.example (safe to commit)
DATABASE_URL=postgresql://user:password@localhost:5432/dbname
API_KEY=your_api_key_here
JWT_SECRET=generate_random_secret

# .env (NEVER commit)
DATABASE_URL=postgresql://produser:X7k!mP9@prod.db.example.com:5432/proddb
API_KEY=sk_live_abc123xyz789
JWT_SECRET=7f3a9b2c8d4e1f6a5b9c3d7e2f8a1b4c

8.1 Performance Targets

Metric Target Critical Threshold

Page Load Time (First Contentful Paint) < 1.5s < 3s
Database Query Time < 100ms < 250ms

8.2 Performance Best Practices

  • API: Implement pagination, use compression, cache responses
